# 3D in Vivid — Architecture & Roadmap

Vivid's 3D support follows the **Hybrid "Scene Fragment"** architecture (Option C from the [architecture report](3d-architecture-report.md)). One new port type carries self-contained scene fragments through operator chains, bridging to the existing 2D texture pipeline via a Render3D operator.

---

## Architecture Overview

The core idea: a **scene fragment** is to 3D what a GPU texture is to 2D — the single data type that flows through wires. A Shape3D operator outputs a scene fragment (geometry + material + transform). Downstream operators modify it. Render3D rasterizes the fragment tree into a GPU texture that feeds the existing 2D pipeline.

```
[Shape3D (cube)] → [Transform3D] → [SceneMerge] → [Render3D] → [Bloom] → output
 color, roughness    rotation ← beat    ↑              ↑
 emission ← beat                   [Shape3D (sphere)]  Camera params
                                    color ← spectrum    built into Render3D
```

**Why this architecture:**
- ONE new port type (`VIVID_PORT_GPU_SCENE`) — mirrors `VIVID_PORT_GPU_TEXTURE`
- Minimum viable result is **2 operators** (Shape3D + Render3D)
- Purely additive — existing 2D operators are untouched
- Fits the operator-chain evaluation model — fragments flow and transform like textures
- Audio-reactivity works identically to 2D (control floats/spreads/textures wire into 3D params)

---

## Scene Fragment Data Structure

A scene fragment bundles everything needed for a draw call:

```cpp
struct SceneFragment {
    // Geometry
    WGPUBuffer          vertex_buffer;      // positions, normals, UVs
    WGPUBuffer          index_buffer;       // triangle indices
    WGPUVertexBufferLayout vertex_layout;   // attribute descriptions
    WGPUPrimitiveTopology  topology;        // triangles, lines, points
    uint32_t            vertex_count;
    uint32_t            index_count;

    // Material
    WGPURenderPipeline  pipeline;           // compiled vertex + fragment shader
    WGPUBindGroup       material_binds;     // uniforms + textures
    WGPUBlendState      blend;
    WGPUCullMode        cull;

    // Transform
    mat4x4              model_matrix;       // world-space transform

    // Composition
    SceneFragment**     children;           // child fragments (from SceneMerge)
    uint32_t            child_count;

    // Rendering hints
    BoundingBox         bounds;             // for frustum culling
    bool                depth_write;        // participate in depth testing
};
```

The fragment accommodates multiple geometry types through the same structure:

| Geometry type | Representation | Notes |
|---|---|---|
| Triangle mesh | Vertex + index buffers, `Triangles` topology | Standard path |
| Point cloud | Vertex buffer, `Points` topology | No index buffer |
| Instanced mesh | Mesh + instance buffer | Instanced draw call |
| SDF / Raymarched | Fullscreen quad + fragment shader | Like current 2D ops, but writes depth |
| Particles | Compute buffer → indirect draw | GPU compute fills vertex data |

## Phased Roadmap

### Phase 0 — WebGPU 3D Infrastructure

Foundation work — no new operators, no new port types. Build the low-level capabilities that every subsequent phase depends on.

**Deliverables:**
- Depth buffer creation and management (texture format `Depth24Plus`)
- Vertex buffer creation utilities with attribute layout descriptions
- 3D render pipeline helper (vertex + fragment shader, vertex buffers, depth stencil state)
- 3D render pass helper (color + depth attachments, clear depth to 1.0)
- CPU-side projection/view matrix computation

**Key files:**
- `src/operator_api/gpu_common.h` — new helpers alongside existing 2D ones: `create_3d_pipeline()` (with `WGPUVertexBufferLayout` + `WGPUDepthStencilState`), `run_3d_pass()` (with `depthStencilAttachment`), `create_vertex_buffer()`, `create_index_buffer()`
- `src/operator_api/gpu_operator.h` — depth texture fields on `VividGpuState` or a new struct
- `deps/glfw/deps/linmath.h` — already provides `mat4x4_perspective`, `mat4x4_look_at`, `mat4x4_rotate`, `mat4x4_translate`, etc.

**What becomes possible:** Nothing user-facing yet, but the scaffolding for 3D rendering exists.

---

### Phase 1 — Scene Fragment Type + Render3D

Define the data type that flows through 3D wires, teach the scheduler to route it, and build the operator that converts fragments to textures.

**Deliverables:**
- `SceneFragment` struct definition
- `VIVID_PORT_GPU_SCENE = 6` port type
- Scene port validation in wire building (scene ports connect only to scene ports)
- Scene fragment routing in the scheduler tick loop
- **Render3D operator**: takes scene fragment input, has built-in camera params (position, target, FOV, near/far), runs a depth-tested render pass, outputs a GPU texture

**Key files:**
- `src/operator_api/types.h` — add `VIVID_PORT_GPU_SCENE = 6` to `VividPortType` enum
- `src/runtime/scheduler.h` — add scene fragment fields to `NodeState` (analogous to `gpu_texture` / `gpu_texture_view`), add `is_scene_wire` to `Wire` struct
- `src/runtime/scheduler.cpp` — scene wire detection in `build()`, scene fragment resolution in `tick()` (analogous to texture input resolution at lines ~507-529), depth buffer allocation in `allocate_gpu_textures()`
- `operators/gpu/render3d/` — new operator directory

**What becomes possible:** The pipeline exists end-to-end, but there's no geometry source yet.

---

### Phase 2 — First Geometry Operator

The milestone phase: a visible 3D scene from two operators.

**Deliverables:**
- **Shape3D operator**: generates built-in geometry (cube, sphere, torus, plane, cylinder) with built-in material params (color, roughness, metallic, emission) and built-in transform params (position XYZ, rotation XYZ, scale XYZ). Outputs a scene fragment.
- Built-in geometry generation (vertex positions, normals, UVs, index buffers)

**Key files:**
- `operators/gpu/shape3d/` — new operator directory
- `operators/gpu/shape3d/shape3d.cpp` — geometry generation, material setup, fragment output
- `operators/gpu/shape3d/shape3d.wgsl` — PBR-lite vertex + fragment shader (Blinn-Phong or simplified PBR)

**What becomes possible:** `Shape3D → Render3D → [any 2D chain]` produces a lit, shaded 3D object on screen. Audio-reactive 3D is immediately available by wiring control signals into Shape3D's material/transform params.

---

### Phase 3 — Scene Composition

Multi-object scenes and external transform control.

**Deliverables:**
- **Transform3D operator**: takes a scene fragment, applies position/rotation/scale from control inputs, outputs modified fragment. Enables separating animation from geometry.
- **SceneMerge operator**: N scene fragment inputs → one combined fragment tree. Enables multi-object scenes.
- **Light operator**: point light and directional light as scene elements or as Render3D params (TBD based on usage patterns)

**Key files:**
- `operators/gpu/transform3d/` — new operator
- `operators/gpu/scene_merge/` — new operator
- Render3D shader updates for multi-light support

**What becomes possible:** Complex scenes — multiple objects with independent transforms driven by audio, combined into one rendered view.

---

### Phase 4 — Advanced Geometry

External assets and geometry manipulation.

**Deliverables:**
- **MeshImport operator**: loads OBJ/glTF files, outputs scene fragment
- **Deformer operator**: vertex displacement (noise, sine wave, audio-driven) on scene fragment geometry
- **Instancer operator**: takes a scene fragment + control spread, outputs instanced rendering (one mesh drawn N times with per-instance transforms/colors)

**Key files:**
- `operators/gpu/mesh_import/` — file loading, vertex buffer construction
- `operators/gpu/deformer/` — GPU compute or vertex shader displacement
- `operators/gpu/instancer/` — instance buffer management, instanced draw calls

**What becomes possible:** Import real 3D models. Deform geometry with audio. Render thousands of instances driven by spread data.

---

### Phase 5 — Particles & Volumetrics

GPU-native generative geometry.

**Deliverables:**
- **Particles3D operator**: GPU compute particle system (emission, forces, lifetime) → scene fragment via indirect draw
- **SDF3D operator**: raymarched signed distance fields → scene fragment (fullscreen quad with depth output for compositing with mesh geometry)
- Camera-facing billboard support in the particle system

**What becomes possible:** Particle effects composited with mesh geometry in the same scene. Raymarched volumes with correct depth interaction.

---

### Phase 6 — Advanced Rendering

Production-quality materials and lighting.

**Deliverables:**
- Full PBR material system with texture map inputs (albedo, normal, roughness, metallic, emission maps)
- Shadow mapping (directional + point light shadow maps)
- Environment mapping / HDRI lighting
- 3D-aware post-processing: SSAO (screen-space ambient occlusion), depth of field using depth buffer output from Render3D

**What becomes possible:** Photorealistic rendering. Shadows and environment reflections. Post-processing that understands scene depth.

## Key Design Decisions

### Depth buffer ownership

The depth buffer lives on Render3D, not on individual geometry operators. Render3D creates a depth texture matching its output dimensions and uses it for the render pass. Geometry operators don't need to know about depth — they just provide fragments.

This mirrors how the existing pipeline works: `VividGpuState` owns the output texture, operators write to it.

### Camera: Render3D params vs. separate operator

**Phase 1-3**: Camera is built into Render3D as params (position, target, FOV, near, far). This keeps the minimum viable operator count at 2 and avoids a separate Camera port type.

**Phase 4+**: If users need multiple cameras, camera animation, or camera-as-scene-element patterns, extract Camera into a separate operator that outputs camera data through the scene port or a dedicated mechanism. The Render3D params become defaults when no camera operator is connected.

### Copy vs. mutate semantics for transforms

Scene fragments use **copy-on-write** semantics. When Transform3D receives a fragment, it copies the `model_matrix`, multiplies in its transform, and outputs a new fragment referencing the same GPU buffers but with the updated matrix. Geometry and material GPU resources are shared (reference counted), only the transform is new.

This means branching is safe: one Shape3D can feed two Transform3Ds with different rotations, and both fragments share the same vertex/index buffers.

### Scene fragment lifetime

Scene fragments are per-frame transients. They're built during `tick()`, consumed by Render3D's draw calls, and discarded. The underlying GPU buffers (vertex data, pipelines, bind groups) are owned by the source operator and persist across frames. This matches how GPU textures work today — the texture persists on `NodeState`, but the reference through wires is per-tick.
